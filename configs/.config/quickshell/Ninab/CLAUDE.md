# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Ninab is a [Quickshell](https://quickshell.org) (QML) desktop shell for NixOS running the Mango window manager. It replaces a traditional desktop bar/widgets with "Nino" — a pill-shaped widget that follows the mouse across monitors and expands into a scrollable card on click, both populated by drop-in **modules** (`modules/*.qml` — clock, volume, etc.) configured via `config.json`. The full product vision (more starter modules like MangoWindows/MangoLayout/Volume, a real kinematics/velocity movement model) lives in the plain-text file `Project` at the repo root — read it before making architectural decisions, since most of this codebase is a step-by-step build toward that spec, not the finished thing.

## Running

```
quickshell -p shell.qml
```

There is no build step, package manifest, linter, or test suite — this is a QML config read directly by the `quickshell` binary. `shell.qml` is the entry point Quickshell loads.

To sanity-check a change compiles/runs without a full manual test, run it against the live compositor for a few seconds and check the log for warnings/errors:

```
timeout 5 quickshell -p shell.qml
ls -t /run/user/$(id -u)/quickshell/by-id/*/log.qslog | head -1 | xargs grep -iE "warn|error"
```

This actually launches overlay windows on the real Wayland session (`$WAYLAND_DISPLAY`), so keep the timeout short.

## Architecture

### Files

- `shell.qml` — entry point. Owns Wayland/layer-shell plumbing (one `PanelWindow` per monitor via `Variants { model: Quickshell.screens }`) and all shared "Nino identity" state (see below). Knows about screens; `Nino.qml` deliberately doesn't. Does **not** do any system I/O itself anymore — that's `logic/System.qml` (see below).
- `Nino.qml` — the pill/card widget itself: position/movement math, expand/collapse, pin button, and hosting the module rows (pill icon row, card default overview, card module-takeover). Written to be screen-agnostic (fed a target point + tunables as plain properties, knows nothing about Wayland/multi-monitor) *and* system-agnostic (hands modules a `system` instance, never touches the OS itself).
- `Theme.qml` / `theme.json` — visual values (sizes, colors, font). `Config.qml` / `config.json` — movement values (angle/distance/leash per pill and card, speed/accel), module layout (`pillModules`, `cardModules`, `moduleSettings`), and `system` tunables (poll intervals, ping host, audio sink targets — fed into `logic/System.qml`). Both use Quickshell's native `FileView` + `JsonAdapter` (see below).
- `logic/System.qml` — the **one place** that calls out to Linux/Mango/system APIs (cursor position, audio, network). See "System.qml" below — this is the file to fork/edit to port Ninab to a different compositor or audio/network stack, and modules never shell out directly.
- `modules/*.qml` — drop-in module content (`modules/clock.qml`, `modules/volume.qml`, `modules/network.qml`); `modules/template.qml` is the documented starting point for a new one. See "Module system" below.
- `ModuleIconSlot.qml` / `ModuleWidgetSlot.qml` / `ModuleIconRow.qml` / `NinoCardContent.qml` — host-owned plumbing that loads and lays out modules; modules themselves never touch clicks or layout directly. See "Module system" below.
- `ModuleSlider.qml` — a bar slider (track + fill, optional circular knob) for any module that controls a 0..1 level. Not module-specific; `modules/volume.qml` is the first user, later ones (brightness, mic gain, ...) should reuse it rather than re-implement. Its own properties (`barHeight`/`cornerRadius`/`showKnob`) are plain and dumb — it doesn't read `Theme` itself. The actual style is a **standalone, global config** under `theme.json`'s `slider` block (`height`, `cornerRadius` — `-1` means "unset, fall back to `height / 2`, a full pill" — and `showKnob`), exposed as `Theme.sliderHeight`/`sliderCornerRadius`/`sliderShowKnob`; every module binds its `ModuleSlider` instances to those three so all sliders across all modules look consistent without each module owning its own slider style. **Gotcha:** `clip: true` in Qt Quick (on any `Item`, including `Rectangle`) is only an axis-aligned bounding-box (scissor) clip — it never follows a `Rectangle`'s own rounded outline. A square-cornered fill sitting inside a rounded, `clip: true` track is *not* clipped into a rounded shape by that; it just paints its square corners straight over the track's rounded ones. The fix is to give the fill `Rectangle` the same `radius` as the track directly, so it's a smaller pill nested inside the bigger one — the same technique real custom QML sliders use (splitting a track into independently-rounded segments) — rather than relying on clipping to do rounding it doesn't do. The knob, when enabled, is deliberately sized bigger than the track (`max(barHeight * 1.7, barHeight + 8)`) so it reads as a handle grabbing the track rather than sitting flush with it, and grows slightly (`scale`, animated) while dragging for tactile feedback — same idea as Qt Quick Controls' own Slider (groove + handle) and the common custom-QML-slider pattern of a bigger circular thumb overlapping a thinner track.
- `Project` — the original design spec / prompt this codebase is being built toward. Not code; treat it as the source of truth for "what should this eventually do."

### The shared-state pattern (read this before touching identity state)

Quickshell's `Variants { model: Quickshell.screens }` creates one **persistent, independent** `PanelWindow` (and one independent `Nino` instance) per monitor — they are not recreated as the cursor moves, they just get shown/hidden. Any state that should feel like "the one Nino" (not five independent copies) — `following`, `expanded`, `pinned`, `cardContent`, `cardScrollY` — is therefore owned once at the `shell.qml` root level and mirrored *down* into every monitor's `Nino` via property bindings, with the toggle/click action *bubbling back up* via a signal (`toggleFollowRequested`, `toggleExpandedRequested`, `togglePinRequested`) that the root handles. `Nino.qml`'s own copies of these properties are just bound mirrors — never write to them directly from inside `Nino.qml`, always emit a signal and let the owner (`shell.qml`) update the shared value. This pattern exists because of two bugs that were fixed this way: a follow-toggle that got silently reset when the cursor crossed monitors, and a card that collapsed back to a pill on a monitor switch.

`activeMonitorName` (which monitor currently hosts the visible Nino) follows the same idea: it only re-syncs to the cursor's current monitor while `following` is true, so "sitting" (`following = false`) pins Nino to its monitor even if the cursor wanders off.

`hovered` is the one piece of state that stays local per-`Nino`-instance — it's a real, transient mouse-over concept tied to whichever window is actually receiving input, and only the active instance ever gets hover events anyway. It's force-cleared on `visible` going false to avoid a stuck-frozen instance (see `onVisibleChanged` in `Nino.qml`).

### Movement model

Nino's on-screen position (`restX`/`restY` in `Nino.qml`) is **not** a continuous 1:1 cursor follow. It only re-anchors when the cursor strays more than `maxDistancePx` from wherever Nino currently sits (`maybeTrackTarget()`), which is what gives you a grace window to walk the mouse up and click it instead of racing a moving target. For an expanded card, exceeding `maxDistancePx` collapses it back to a pill instead of re-anchoring — unless `pinned` (toggled via the small corner button, which also blocks that same auto-collapse) — since dragging the much bigger card around behind a wandering cursor felt wrong. Two anchoring modes for repositioning, selected by `angleFree`:
- **Fixed-angle** (default): re-anchors to `distancePx` away from the cursor at a fixed compass `angleDegrees` (0° = straight up, clockwise).
- **Free-angle**: ignores `angleDegrees` and instead preserves whatever direction Nino was already sitting at relative to the cursor, just enforcing `distancePx` — like a leash of fixed length getting pulled taut rather than reset to a side.

Pill and card have fully independent `angleDegrees`/`angleFree`/`distancePx`/`maxDistancePx` (`Nino.qml`'s `effective*` properties pick the right set based on `expanded`), since a distance/leash that feels right for the small pill can feel wrong once the much bigger card is showing.

`speed`/`accel` are read from config and passed through to `Nino` but **not yet acted on** — movement is still a fixed-duration eased animation (`followDurationMs`, `Behavior on x/y`). They're reserved for a real velocity/acceleration curve once the `logic/Kinematics.js` step from the `Project` doc is built; don't try to fake that mapping onto the current `Behavior`-based animation.

### Click semantics

Left click on the pill opens it into a card. Once expanded, left/right click on the card body are claimed by module content (see "Module system" below) — there's no plain-click-to-collapse. The only ways a card closes are the leash (see "Movement model" above), or manually via a module/host action (the back button clears a module takeover; nothing currently collapses the card itself back to a pill via click — that's expected, matches the `Project` doc). Middle click toggles `following` in both pill and card mode. The pin button (`pinButton` in `Nino.qml`, an 11px circle in the card's top-right corner) and the back button (a `Canvas`-drawn upward triangle, mirrored in the top-left, only visible during a module takeover) both have their own `MouseArea`s, declared after — and so stacked above — everything else, so their clicks are claimed before reaching module content or the big expand/follow `MouseArea` underneath.

### Module system

A module is one file in `modules/`, referenced by lowercase filename with no `.qml` (`modules/clock.qml` ↔ `"clock"` in config) — copy `modules/template.qml` to start one; it documents the full contract in its header comments. In short: a module is a single `Item` with three views (`icon`/`widget`/`card`) switched by a `displayMode` property the host sets, declares `hasIcon`/`hasWidget`/`hasCard` (not every module needs all three), reads `theme` (the whole `Theme.qml` instance, for visuals) and `system` (the whole `logic/System.qml` instance, for live data/actions — see "System.qml" below) and `config` (its own settings sub-object) with its own fallbacks, and implements `activateIcon()` for "my icon got left-clicked in the card" (no-op is fine). **A plain `Item`'s `width`/`height` don't auto-follow `implicitWidth`/`implicitHeight`** the way `Text` or a positioner's would — every module needs `width: implicitWidth; height: implicitHeight` explicitly (see the comment in `template.qml`) or it silently renders at 0×0 despite computing a correct implicit size. This bit `ModuleIconSlot.qml`/`ModuleWidgetSlot.qml` too before it was caught.

Click handling is centralized in the host, not the module, using the same "just don't accept that mouse button, let it fall through" trick as the pin button:
- **`ModuleIconSlot.qml`** hosts one module in icon mode. `interactive: false` (pill context) only accepts right-click, so left clicks fall straight through to Nino's own expand handler underneath — no pass-through plumbing needed, that's just how an unaccepted button propagates. `interactive: true` (card context) accepts both: left calls `activateIcon()`, right requests a card takeover.
- **`ModuleWidgetSlot.qml`** hosts one module in widget mode (card-only, full row width — width is set externally, never by the slot itself). Its own right-click-only `MouseArea` sits *underneath* the loaded widget in stacking order, so a widget's internal controls (sliders, etc.) get left clicks normally, while right-clicks the widget doesn't itself consume fall through to request a card takeover.
- **`ModuleIconRow.qml`** is a `Flow` of `ModuleIconSlot`s from a name list — shared by the pill's icon row (`interactive: false`, clipped, no scroll — overflow modules are just cut off, not wrapped/scrolled, per the `Project` doc's "pill won't expand or scroll" rule) and a contiguous run of icon modules inside the card's default view. It also owns `alignment` (`"left"`/`"center"`/`"right"`, config: `pill.alignment`, only exposed for the pill — card rows stay left-aligned): `Flow` always lays children out starting at its own `x:0` regardless of how wide it is, there's no built-in "justify a row that doesn't fill its width," so `ModuleIconRow` computes the actual space its content used via `childrenRect.width` (which reflects Flow's real wrap-aware layout even when `width` is set to the full available space) and offsets its own `x` by the leftover. Wrapped multi-row content just ends up left-aligned internally since `childrenRect.width` is then close to the full `width` anyway — nothing meaningful left to center/right-align at that point.
- **`NinoCardContent.qml`** is the card's default (non-takeover) body: chunks the ordered `cardModules` config list into contiguous icon-flow segments and full-width widget rows, in list order, inside a `Flickable` (unlimited modules, scrollable per the `Project` doc).

Right-clicking any module (pill or card, icon or widget) sets `Nino.cardContent` to that module's name via the `moduleCardRequested` signal, which `shell.qml`'s `openModuleCard()` handles by also forcing `expanded = true` — so right-clicking a pill icon both opens *and* jumps straight to that module's card view in one action. `cardContent == ""` means the default overview; the back button (top-left, card mode) clears it back to `""` without collapsing the card itself. A module's own `card`-mode view is loaded full-size via a plain `Loader` in `Nino.qml` (`takeoverLoader`) — if a module's card content is taller than the card, wrapping it in its own `Flickable` is the module's job, the host doesn't force one.

Switching between the default overview (`NinoCardContent`) and a module takeover (`takeoverLoader`) animates as a "shuffle": whichever is becoming current rises from underneath (`y` offset shrinking to 0, `scale`/`opacity` up, `z` on top via `cardArea.showingDefault`), whichever is leaving sinks the same way in reverse. This only ever needs to animate between those two fixed elements — never module-takeover to a *different* module's takeover directly — because the icon/widget rows that trigger a takeover live inside `NinoCardContent`, which is only visible while showing the default overview in the first place; there's no way to right-click a second module without passing back through the overview first.

**Gotcha:** a module file in `modules/` doesn't automatically see host-side types declared at the repo root (`ModuleSlider.qml`, etc.) — `modules/` is a different QML implicit-import directory, same reason `ModuleIconSlot`/`ModuleWidgetSlot` load a *module* via a `Loader { source: "modules/" + name + ".qml" }` string path rather than a direct type tag. A module that wants to *use* a root-level component (like `ModuleSlider`) needs `import ".."` at the top of its file — `modules/volume.qml` needs this for `ModuleSlider`, `modules/clock.qml` doesn't need it since it doesn't reference anything outside its own file.

**Gotcha:** don't name a property the same as an outer `id` you're binding it from — e.g. `Nino { theme: theme }` where Nino has `property var theme` looks correct but the unqualified right-hand `theme` resolves to Nino's *own* property (self-reference, always `null`) instead of the outer instance, because the object being constructed is part of the scope chain too. This is why `shell.qml` names its instances `themeInstance`/`systemInstance`, not `theme`/`system`. This exact bug once threw an unrelated-looking cascade of `ReferenceError: Layer/KeyboardFocus is not defined` on the `Quickshell.Wayland` lines further down the same object — if you see spurious errors on lines you didn't touch, suspect a real binding error earlier in the same object first.

### System.qml — the system-agnostic bridge

**Why this exists:** two problems, one fix. First, performance — `volume.qml`/`network.qml` each get instantiated multiple times (pill, card row, monitor ×N), and when they owned their own `Process`/`Timer` code directly, *every instance* independently re-ran the same `wpctl`/`nmcli`/`ping` calls, including on monitors that aren't even visible (`visible: win.isActive` only hides rendering, it doesn't stop bindings/Timers). Second, portability — the Project doc's goal of modules/Nino being screen- and system-agnostic meant every OS-specific call needed one home, not one per module. `logic/System.qml` is that home: instantiated exactly once in `shell.qml`, handed down to every module alongside `theme` (same "hand down the whole instance" pattern, same self-shadowing gotcha above — see `Nino.qml`'s `system` property). Forking Ninab for a different compositor/audio/network stack means editing this one file's `Process` commands, not touching Nino or any module.

**What it owns**, each with its own poll `Timer` (rates configurable via `config.json`'s `system` block, fed through `Config.qml`):
- **Cursor** (`cursorX`/`cursorY`/`cursorMonitor`) — polls `mmsg get cursorpos`. `mmsg` has a real streaming `watch` mode for several queries (monitor/client/tag/keymode/...) but **not** cursor position, so polling is the only option here; this didn't move to a watch-based design because there isn't one to move to.
- **Audio** (`volume`/`muted`/`micVolume`/`micMuted`/`appStreamMeta`/`appVolumes`) — drives `wpctl`. Optimistic-update-then-reconcile: `volume`/`muted` flip immediately on a user action, the next poll corrects it if wrong — sidesteps needing to know `wpctl`'s exact exit semantics.
- **Network** (`primaryIface`/`connectionType`/`connectionName`/`ipAddress`/`wifiSignal`/`pingMs`/`rxRate`/`txRate`/`availableNetworks`) — drives `nmcli`/`ip route`/sysfs/`ping`.

**The id-dispatch pattern:** `valueFor(id)`/`setValueFor(id, v)`/`showMutedFor(id)`/`toggleMuteFor(id)` on `System` resolve `"volume"`/`"mic"`/any per-app-stream id to the right internal state, so `volume.qml`'s widget/card rows can be one generic component (`SliderControlRow`) instead of one block of QML per kind — the module doesn't know or care where a given id's value actually comes from.

**Visibility-gated polling:** `shell.qml`'s `visibleCardModule` (`expanded ? cardContent : ""` — not `cardContent` alone, which doesn't reset on collapse and would otherwise misreport a leash-collapsed card as still showing) feeds `System.activeCardModule`. Expensive, card-only data — wifi scan (`availableNetworks`), signal %, `pingMs`, and volume's per-app `appStreamMeta`/`appVolumes` — only refreshes on its own poll while `activeCardModule` matches the owning module; primary status needed for icon/widget mode (`volume`/`muted`, `connectionType`/`rxRate`/`txRate`) always refreshes regardless. An `onActiveCardModuleChanged` handler immediately kicks off a fetch for whichever module just became visible, rather than leaving it stale until the next regular poll tick — verified this actually fires within ~200ms of opening a card, not waiting out the full poll interval.

**Cursor polling: gated on `following`, and adaptive.** `System.following` (fed from `shell.qml`'s `root.following`) gates the cursor `Timer`'s `running` directly — while "sitting" (`following: false`), Nino ignores cursor movement anyway (`Nino.qml`'s `maybeTrackTarget`), so `logic/System.qml` doesn't poll `mmsg` at all, verified by driving a real `following` toggle and confirming `cursorX`/`cursorY` stayed frozen bit-for-bit for the entire "sitting" window, not just close. On top of that, polling is adaptive even while following: `cursorPollIntervalMs` (fast) is used while the cursor's actually moving, backing off to the slower `cursorIdleIntervalMs` after `cursorIdleAfterTicks` consecutive unchanged reads, snapping straight back to the fast rate the instant it moves again — verified against real mouse movement, including the exact tick where it crossed the threshold and switched. `triggeredOnStart: true` on the cursor `Timer` means resuming from "sitting" (or app startup) polls immediately rather than waiting out a full interval first; `onFollowingChanged` also resets the backoff state on resume so it tracks crisply again rather than picking up wherever it left off before sitting.

**Gotchas, all found by testing on this machine, not assumed — keep them in mind before touching System.qml:**
- **No reliable per-channel (left/right) balance control exists.** `wpctl` has no per-channel option. Writing PipeWire's `channelVolumes` directly via `pw-cli` (same package as `wpctl`, not a new dependency) looked like the fix, but two separate real attempts — the node's `Props`, then the device's active `Route` param (found via `pw-cli e <device-id> Route`) — were both silently overridden: the write succeeds, read-back briefly shows the new value, but `wpctl get-volume` never reflects it and it doesn't persist. WirePlumber (the session/policy manager `wpctl` itself talks to) owns and continuously re-asserts volume state for ALSA hardware devices; a raw `pw-cli` client poking those params loses that fight with no error anywhere. The one path that would work, `pactl set-sink-volume <sink> <L>% <R>%`, needs `pactl`, not installed here — intentionally left unbuilt rather than shipped half-working.
- **`wpctl status`'s "Streams:" table doesn't print a volume for stream entries** the way it reliably does for Sinks/Sources, confirmed against a real playing app (Vivaldi) — even though the volume genuinely exists (`wpctl get-volume <id>` returns it fine). So `parseAppStreamMeta` only extracts *who* is streaming (id + name); volume/mute per id comes from a separate `wpctl get-volume <id>` each (`appVolumeInstantiator`, a `QtQml.Models` `Instantiator` keyed on the current id list). Each entry also has indented port-link sub-lines underneath that would otherwise match the same `<id>. <name>` shape — filtered by indentation depth against the section's first entry, not content. The section ends at the first blank line (the real boundary, confirmed against real output), not "first line we don't understand."
- **A freshly-instantiated `Process` does NOT auto-run** — `running` defaults to `false`. The plain volume/mic `Process`es only fire because their poll `Timer` explicitly sets `.running = true`; the `Instantiator`-created per-app `Process` needs `running: true` in its own delegate declaration or it silently never executes (no error, no warning, just no output). This cost a full instrumented test pass to catch — "no errors in the log" looked identical to "working" until `appVolumes` was checked directly and found empty.
- **`appStreamMeta` (id+name) and `appVolumes` (the values) are deliberately separate properties, never merged into one list used as a Repeater model.** A per-row volume drag calls `setAppVolume()` on every pointer-move tick; if that rebuilt a merged list, the Repeater would see a new array every tick and destroy/recreate every delegate (no fine-grained diffing for a plain `var` model), killing the drag after the first move — a real bug, already hit once, fixed by keeping the id list stable and reading live values through `valueFor(id)` instead.
- **`nmcli -t` (terse) escapes `:`/`\` within field values with a leading `\`** — a plain `split(':')` breaks on a value that legitimately contains a colon (an SSID could, in principle). `splitTerse()` undoes that escaping while splitting.
- **No wifi hardware on the machine this was built/tested on**, so the wifi scan/connect/password path (`availableNetworks`/`connectWifiOpen`/`connectWifiSecured`) was only checked structurally (correct `nmcli` syntax per its docs, parsing against hand-written sample lines) — `nmcli dev wifi list` here always returns empty, which is handled the same as "no networks found" (that part *is* live-verified), but a real scan/connect never ran. Check here first if it doesn't work on real wifi hardware.
- **The wifi password field needs real keyboard input**, which is why `shell.qml`'s `WlrLayershell.keyboardFocus` changed from `None` to `OnDemand` (see the comment there) — nothing before this needed keyboard input at all. `OnDemand` only grabs focus when something inside (a `TextInput`) actually requests it, releasing it otherwise, so it doesn't affect the click-through/pointer behavior (a separate mechanism — see "Multi-monitor click-through" below).

`modules/volume.qml`'s own config (unrelated to System — this is display-only) takes a `sliders` array of `{id, icon, mutedIcon, label, labelIcon}` entries (validated with the same `isArrayLike` duck-typing as `Config.qml`'s `pillModules`/`cardModules`, since it's a nested array inside `moduleSettings`, a freeform `var` blob — same `Array.isArray()` gotcha applies). Only `"volume"`/`"mic"` resolve to real data via `system`; any other id is parsed but silently skipped rather than shown as a dead control — the intended extension point for a future slider. Its "Applications" group (one row per live audio stream, via `system.appStreamMeta`) needs no extra dependency: `wpctl status`/`set-volume`/`set-mute`/`get-volume` accept any object id, not just a sink/source alias.

### Config/theme loading (`Theme.qml`, `Config.qml`)

Both use Quickshell's native `FileView` + `JsonAdapter` (`Quickshell.Io`), not custom parsing:
- The `.qml` file's root element *is* a `FileView` (not wrapped in a plain `QtObject` — `QtObject` has no default property in this Quickshell version, so a `FileView` child inside one fails with "Cannot assign to non-existent default property").
- `JsonAdapter { property JsonObject foo: JsonObject { ... } }` is how nested JSON grouping works (used for `pill`/`card`/`system` sections in `config.json`, `pillSize`/`cardSize`/`slider` in `theme.json`). `config.json`'s `system` block (poll intervals, ping host, audio sink targets) is `logic/System.qml`'s tunables — shell.qml wires `Config.cursorPollIntervalMs`/etc into the `System{}` instance the same way it wires `Theme.xxx` into `Nino{}`.
- Missing file → auto-created with defaults (`onLoadFailed` → `writeAdapter()`). Wrong-typed value → `JsonAdapter` logs a warning and keeps the QML-declared default (no crash). External edits are live-reloaded (`watchChanges: true` + `onFileChanged: reload()`).
- Both files add their own `readonly property` layer on top of the raw adapter (`numberOr`/`nonNegative`/`wrapDegrees`/`boolOr` helpers) to also catch values that parse fine but are nonsensical (negative sizes, out-of-range angles) — `shell.qml` and `Nino.qml` should always read the validated `Theme.xxx`/`Config.xxx` properties, never `adapter.xxx` directly.
- **`Array.isArray()` returns `false` on a JSON array read off a `JsonAdapter` `property var`** (e.g. `adapter.pillModules`), even though it behaves like a real array in every other respect — indexable, correct `.length`, `.filter()`/`.map()` work fine on it. A validator written as `if (!Array.isArray(value)) return fallback` silently discards every real array and always returns the fallback, with no warning anywhere (it's not a deserialize error, just a check that looks reasonable and isn't) — this is exactly what made `pillModules`/`cardModules` render as empty despite `config.json` having real content, and it cost a real debugging session to track down since every other layer (the JSON file, the adapter's raw value, individual array elements) checked out fine in isolation. `Config.qml`'s `isArrayLike()` duck-types instead (`typeof value.length === "number" && typeof value.filter === "function"`) — use that, not `Array.isArray`, for any future array-shaped config value.

### Multi-monitor click-through

Each `PanelWindow`'s `mask: Region { item: ... }` controls what part of that monitor is actually clickable (everything else passes through to whatever's beneath) — it's always just `nino`'s own bounds, pill or card. An earlier version tried to also claim the full monitor while expanded (to catch a click outside the card and collapse it), but that meant a click on the desktop behind an open card was swallowed instead of reaching whatever was underneath. Wayland surfaces don't support "catch this click and also forward it to the surface below" — an accepted event is exclusively yours — so that would've needed synthetic input injection (`ydotool`/`wtype`/compositor IPC) to fix properly, which wasn't worth the dependency. Card-closing-on-distance (see "Movement model" above) replaced it instead.

### Cursor tracking

Wayland doesn't expose global mouse position to a click-through layer-shell surface, so `logic/System.qml` polls `mmsg get cursorpos` (Mango's IPC client) on a `Timer` and parses JSON output (`x`, `y`, `monitor` fields) into `cursorX`/`cursorY`/`cursorMonitor`. If `mmsg`'s output shape differs on your Mango version, that parsing is the place to fix it. The `Project` doc originally called for this to become a swappable `logic/MouseTracker.qml` with multiple backends — `logic/System.qml` now serves that role (one file, one place to swap the backend), so a separate `MouseTracker.qml` isn't needed on top of it.
